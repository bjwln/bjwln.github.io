# 文献

## A survey on LLM-based multi-agent systems: workflow, infrastructure, and challenges

### 论文框架

本文在Introduction部分介绍了统一的智能体的框架，该框架包含五个部分

1. **Profile：agent如何被创建和选用？**
2. Perception：agent如何感知环境的信息来丰富自己的知识库？
3. SelfAction：agent如何利用记忆机制来储存信息？如何进行推理复杂的任务？
4. **Mutual interaction：多agent系统中，智能体如何相互通信？**
5. **Evolution：智能体如何通过自我批评来使得自我进步？**

### MAS算法支撑

每个agent能够独立感知环境并做出决策，还可以通过模拟现实世界中的协作模式(如合作、 竞争和分层组织)与其他智能体进行交互，从而提高整体的协作效率。这通常通过融合控制理论与强化学习方法来实现，在MAS中，MARL算法是核心的技术。Marllib（引用的）等人根据四个维度对这个算法进行区分：

1. task patterns
2. agent types
3. learning styles
4. knowledge sharing

### MAS系统的结构分类

**`[25]`这篇文献根据MAS的特征可以将其分为两类，这是层次划分**

1. agent-level（智能体层面）：看单个智能体本身长什么样，比如它有什么能力、是同质还是异质。
2. system-level（系统层面）：看整个系统怎么组织，比如通信方式、控制结构。

**`[26]`提出可以用以下两个维度交叉出四种原型，这是维度划分 **

1. agent heterogeneity（智能体异质性)：智能体是都一样，还是各不相同；

   - homogeneou（同质智能体）：几个智能体能力、角色相同，干类似的活；
   - heterogeneous（异质智能体）：每个智能体有不同专长，靠各自能力互补协作。

   在 MDT 中：五个"影像科医生智能体"一起读片子就是同质；一个肿瘤内科、一个影像科、一个病理科组队就是异质。异质组合的价值就是互补。<u>结构越灵活，系统越能适应不同任务和环境变化；异质智能体之间能互补、产生协同效应</u>

2. communication level（通信水平）：智能体之间通信是少还是多、是平级还是分层

**其中通信水平可以由`[23]` 给出的【通信机制 = 通信范式(通信协议) + 通信结构 + 通信内容】来进一步刻画**

- `[27]`提出通信范式（协议）有四维框架，重点区分了两类系统
  - blackboard（黑板系统）：所有agent共享一块"黑板"，把消息写上去、其他人自己来读，类似共享消息池；
  - message-based（消息系统）：agent之间直接发消息，点对点传；

- 通信结构分为四种类型,包括去中心化、集中式、分层或嵌套。

###  MAS profile

#### 上下文生成方法：“先有任务，再定制画像”

根据特定上下文或用户的具体要求,代理配置文件可能包含不同类型和内容的信息。可根据这些信息生成智能体画像。上下文化生成方法灵活地基于复杂任务的环境确定智能体档案的类型和内容,确保与任务需求的最优对齐。然而, 这种方法既是一次性的,又劳动密集,因为它需要为每 个新场景重新生成智能体档案。

这种成本高，与任务的对其程度高

#### 预定义方法： “先造好人才池，任务来了再挑人”

在此方法中,大语言模型(LLMs) 被广泛用于定义多个agent共同形成智能体池。当面对特定场景时,从该池中选择合适的agent来执行相关的子任务。通常,LLM在提示中明确代理配置文件的组成和属性,LLM利用这些来生成具有不同特征的agent。随后,合适的agent要么由人工指定,要么由LLM选择。最后,LLM负责更新智能体的状态信息,以便于它们的恢复或后续行动。

这种成本低，与任务的对其程度低

#### 基于学习的方法

中和以上两种方法。在为特定场景定义代理配置文件的同时节省大量时间。然 而,在生成新智能体时存在潜在问题,例如大型模型幻 觉以及生成的配置文件与相应任务之间的不匹配。

### MAS Mutual interaction

MAS的相互交互可以分为三个基本组成部分

- Message Delivery（消息传递）
- Interaction Structure（交互结构）
- Interaction Scene（交互场景）

#### Message Delivery

消息通常以文本形式记录和传输,尽管一些工作也整合了多模态信息,如视觉和音频数据。消息的内容会根据任务分配和交互场景动态变化,通常包含历史和当前状态信息以及其他智能体的通信消息。

通常,消息传递由任务分配、与其他智能体的交互或外部控制信号触发,或智能体先将消息存储在共享内存池中,其他智能体可以从中检索信息 。

#### Interaction Structure

交互结构定义了多智能体系统内的通信框架,通常基于消息内容进行组织和安排,从而为智能体分配不同的角色和责任agent。交互结构可分为四种类型:

- 分层式（Hierarchy）

  在层级交互结构中,不同级别的智能体 扮演不同的角色,高级智能体和低级智能体之间有明确 的区分。高级智能体通常扮演监督角色,做出关键决策 并向下级智能体发布指令。这种交互模式模仿了传统的 组织结构,并通过明确划分权力和责任边界来提高效率。

- 去中心化（Decentralized）

  去中心化通信在智能体直接相互通信而不依赖中央权威的对等网络中运行。这种结构不仅促进了智能体之间的平等,允许更灵活和动态的交互,还减少了单个大语言模型的计算负担,增强了系统的鲁棒性。 然而,当应用于大规模系统时,协调和通信开销可能会 变得显著,可能影响整体性能。

- 集中式（Centralized）

  在集中式交互结构中,一个中心智能体或一组中心智能体协调系统,管理并编排所有智能体之间的交互。这种结构集中了控制和协调,简化了决策过程, 避免了潜在冲突,并提高了整体系统效率。然而,由于系统依赖于中心智能体,它容易受到单点故障和通信延迟的影响,使得难以快速响应环境变化。

- 共享消息池（Shared Message Pool）

  共享消息池是一种大语言模型智能体之间信息交换的机制,其中智能体通过共享消息池发布和订阅信息。这种结构允许智能体根据其需求获取相关信息,而无需直接点对点通信,从而提高通信效率。优势包括简化的通信过程、降低信息传输的复杂性以及统一的消息管理方法。然而,多个智能体同时访问共享消息池可能导致争用和同步问题。

#### Interaction Scene

在MAS中按场景内容可分为三类

- 通信场景（communication）

  智能体通过交换信息进行协调和决策。这种信息交换可以采用直接形式,例如通过特定通信渠道 传输每个智能体的状态、计划和建议, 或间接形式,例如共享关于环境、任务或其他智能体的知识。

- 任务执行（task execution）

  任务执行场景关注智能体如何根据预定义的任务分配来执行特定行动,这可能包括角色扮演游戏, 分布式任务分配等等

- 环境探索（environment exploration）

  环境探索场景要求智能体利用感知和学习机制,在未知环境中不断适应和优化其行为,这可能包括模拟的和真实的物理环境。

在MAS中按场景中智能体之间的关系可分为三类

- 协作式（Cooperative.）

  在协作交互场景中,智能体共同工作以实现共同目标。现有的多智能体协作模型主要分为：

  - 无序协作：它通过构建一个允许多个ChatGPT实例通信、提供反馈和集体思考的网络,促进智能体之间的自然协作,无需固定的角色分配。
  - 有序协作：通过将标准操作程序(SOPs)编码为提示序列,实现有序协作, 使智能体能够根据分配的角色和专业知识执行特定任务。

- 对抗型（Adversarial.）

  在对抗型交互场景中,智能体之间是竞争关系,各自追求自身利益最大化。基本流程包括目标设定、策略制定、交互游戏和结果评估。智能体首先设定目标以最大化自身利益,然后根据对手的行为基准制定竞争策略。在交互游戏阶段,智能体通过交互来实施策略,以争取最大利益。最后,智能体评估游戏结果并调整策略以应对未来的竞争。

- 混合型（Mixed.）

  混合型交互场景结合了协作式和对抗式交互的特点,要求智能体在合作与竞争之间找到平衡。这 种交互类型可以进一步细分为并行和层次化两种形式。

  - 并行(Parallel)：:在并行交互中,智能体独立地在不同任务上协作,共享一些信息而互不干扰。并行处理策略允许多个大语言模型智能体进行协作,每个智能体负责生成答案的独立部分,最终汇总成一个完整的响应,从而实现快速高效的响应生成。
  - 层次化（Hierarchical）：在层次化交互中,智能体之间的关系通常表现为树状结构。父节点智能体设定全局目标,分解任务,并将任务分配给子节点智能体。子节点智能体执行具体任务并提供执行反馈。父节点智能体根据反馈调整全局策略,以优化整体任务执行。

### MAS Evolution
